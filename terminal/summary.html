Executive Summary

Tradebot1 — a live Kalshi demo-environment command center for the five requested verticals (gas prices, elections, culture, crypto, golf), with $0.10+ swing alerting, a model-approved high-ROI feed, simulated strategy research, and transparent verification. Prepared 2026-11-22 (UTC).

1 · The ask, condensed

  1. Collect, organize, analyze the Kalshi demo environment (Trade API v2; REST + WebSocket).
  2. Live dashboard of highest-dollar open events in gas, elections, culture, crypto, golf; track until resolved (YES/NO).
  3. Real-time alerting for swings ≥ $0.10 either way, rendered as two scrolling feeds: all events and model-approved high-ROI.
  4. Simulated trade execution for strategy testing; portfolio performance on the demo account; trade categorization; strategy creation from trade types.
  5. Live interactive charts (X = time — seconds/minutes/hours; Y = contract price) and per-price liquidity (contracts available at each price).
  6. Suggestions to make the site more live/interactive; simplified graphs; every sharp move (≥ $0.10) paired with possible-cause links.
  7. GitHub Pages site; landing page + categorized subpages; tables; clean dashboard UI; everything verified or flagged.

3 · Environment & the single biggest constraint

The build sandbox has no route to the Kalshi demo API (direct connections time out; only github.com and package registries are reachable), and no Kalshi demo API keys were provided. Consequently: (a) every live number on this site is fetched in the visitor's browser at page-open time, not baked in; (b) no historical demo data could be captured to validate alert thresholds empirically; (c) order placement on the demo account is implemented but not exercised — it is gated behind an explicit in-browser setting. Nothing on this site presents an unverifiable number as fact; rows that fail verification are blank and flagged.

Now measured, not assumed: a GitHub-hosted runner in this repository requested the public demo endpoints with this site's origin and got permissive CORS (Access-Control-Allow-Origin echoing the Pages origin, HTTP 200 on markets/order book/candles on both demo hosts) — so public data does load directly in the browser. The same probe confirmed signed requests and unsigned WebSocket upgrades are rejected (probe/results.json ↗).

Second hard constraint, discovered from official WebSocket documentation: Kalshi's WebSocket handshake requires the same signed KALSHI-ACCESS-* headers as REST, and browsers cannot set custom headers on a WebSocket upgrade. The dashboard therefore defaults to authenticated-header-free REST polling (public data) and treats WebSocket streaming as an optional proxy integration — see Suggestions P0.

4 · Architecture

Visitor's browser (GitHub Pages static site, no build step)
  │
  ├─ Public reads (no key):  GET /events?status=open&with_nested_markets=true
  │                          GET /markets/{ticker}/orderbook · GET /exchange/status
  │                          GET /series/{series}/markets/{ticker}/candlesticks (used by tooling)
  ├─ Signed reads/trades (user's demo key, localStorage only):
  │                          GET /portfolio/balance · GET /portfolio/positions
  │                          GET /portfolio/fills · GET /portfolio/orders?status=resting
  │                          POST /portfolio/events/orders (V2; opt-in, untested from this origin)
  ├─ WS proxy (optional, not included): adds KALSHI-ACCESS-* to handshake → ticker/trade/orderbook_delta
  └─ Fallback: clearly-labeled SIMULATED feed (random-walk) when the API is unreachable

All pages are dependency-free vanilla JS + a hand-rolled canvas chart; there is no backend and no database. State (paper ledger, alert log, equity history, settings) lives in the browser's localStorage under the tbs_ prefix.

5 · The high-ROI model (transparent, not predictive)

The “Model-approved” feed filters the same ≥ $0.10 swing alerts down to contracts scoring ≥ 65 / 100. The score is a documented heuristic assembled from fields the dashboard already fetches:

ComponentPointsWhy
Base30Every tracked contract starts here.
Liquidity rank by est. notional (vol × last)+25 top-decile / +18 top-quartile / +10 top-halfThin books move $0.10 on noise; liquid books move on information.
Spread (yes ask − yes bid)+20 ≤ 3¢ · +12 ≤ 7¢ · +6 ≤ 12¢Round-trip cost discipline.
Decisive move magnitude+15 ≥ $0.10 · +8 ≥ $0.05Confirms the alert is a dislocation worth studying.
Favorable entry band $0.55–$0.85+8Meaningful upside with real probability weight.
Open interest ≥ 50k (+7) / ≥ 10k (+4)≤ +7Resolution liquidity and crowding signal.

“Implied ROI if YES” shown in tables = (1 − P)/P — pure arithmetic. The model has no historical calibration yet (no settled demo history was captured; see Flagged). Treat it as a prioritization screen, never as a buy signal.

  • Public market-data endpoints need no key; /portfolio/* and WS do; demo keys ≠ production keys — api_keys ↗

7 · Risks & honest caveats

  • Demo markets are shallow and occasionally repriced by admin action; $0.10 alerts may fire on seed/test prints, not news.
  • “Possible drivers” links are search/reference entry points — never proven causation. Each is labeled as such in the UI.
  • Est. 24-hour turnover (24 h contract volume × current price) is a derived proxy, not an official Kalshi metric; it exists to rank $ magnitude, nothing more. The dashboard prints it as “est.” wherever it appears.
  • The schema's one-day comparison (previous_price_dollars) tells you a contract moved $0.10 within a day, not when inside the day. Only the alert feeds carry observation timestamps, and a swing that opened and closed between two 30-minute collector samples is invisible to the server log.
  • Fees everywhere on this site are the general taker fee with multiplier M = 1. The published schedule has per-series multipliers, some of them zero, which are not modelled — see F-17.
  • “Model-approved” means a market passed a published screen. It has never been calibrated against outcomes and is not a prediction — see F-09.
  • Paper ledger marks come from browser-local state and may lag; reconcile against the demo account before acting.
  • Strategy Lab results are Monte Carlo on synthetic paths. They verify the harness and fee model; they are not predictive.
