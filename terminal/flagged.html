F-01 · No live demo data could be captured or verified in the build session

What: the sandbox running this build has no network route to external-api.demo.kalshi.co (curl → timeout). No Kalshi demo API keys were provided. All prices, volumes, order books, model scores and alert histories shown at runtime are fetched in your browser, never during the build, and contain zero invented values. The offline fallback is a random-walk generator badged SIMULATED.

Unblocks when: someone opens the site in a browser with internet access (GitHub Pages serves it publicly), or a CI/hosted runner with egress to the demo API snapshots data server-side.

F-02 · CORS behavior of the demo REST API from a GitHub Pages origin is unknown

What: Kalshi's public docs specify no Access-Control-Allow-Origin policy for browser clients. If the demo host does not return permissive CORS headers, every live page degrades to its error state, and the user must click “Load simulated feed”. The code handles this gracefully by design, but it has not been exercised against the real origin.

Unblocks when: a browser session with devtools open loads the dashboard and reads the console; or a ~20-line Cloudflare Worker proxy (see Suggestions P0-1) is deployed with Access-Control-Allow-Origin: *.

F-03 · WebSocket streaming requires a proxy — not implemented

What: the demo WS handshake is signed (KALSHI-ACCESS-* headers over GET /trade-api/ws/v2); browsers cannot attach headers to new WebSocket(...). The dashboard therefore polls REST. A wsProxyUrl setting exists and the proxy contract is documented, but no proxy ships with this repo and none was tested.

Unblocks when: a small proxy (Node/Cloudflare/Deno) adds the three headers and forwards the stream; then set wsProxyUrl in Portfolio → Settings.

F-04 · Demo order placement never executed — request shape is best-effort

What: POST /portfolio/events/orders (V2) is implemented in assets/js/kalshi.js with fields corroborated from third-party sources (ticker, side: bid|ask, fixed-point price string, count, time_in_force, self_trade_prevention_type, client_order_id). Exact enum values and any additional required fields have not been validated against the demo API. Worst case: HTTP 400 with a descriptive body, displayed in a toast — no funds can move (mock funds), but no promise of a successful order is made.

Unblocks when: demo keys are supplied and one order is placed from a controlled browser session, or Kalshi's official OpenAPI spec is checked into the repo and the payload is generated from it.

F-08 · “$0.10 in either direction” is operationalized two ways — confirm the intent

What: alerts fire on |Δ| ≥ $0.10 vs (a) the session reference price at first sight, or (b) the price ~2 minutes ago (rolling). A ≥ $0.10 move can therefore alert twice (once per reference) or miss a slow drift through both windows. There is also a 90-second per-contract cooldown to prevent feed spam. If you want strictly one definition — e.g., vs 24h-ago price from candlesticks — that changes assets/js/model.js only.

F-09 · Model score has no empirical calibration

What: the ≥ 65 “model-approved” threshold is asserted from first principles (liquidity, spread, move, entry band, open interest), not fitted to settled-event outcomes. No settled demo history was available to fit it. Treat the feed as a prioritization screen; review its hit rate weekly and refit.

F-10 · “Possible drivers” links cannot prove causation

What: on a ≥ $0.10 alert the chart panel shows a Google News search for the event title plus official reference links for the vertical (e.g., EIA for gas, FEC for elections, CoinGecko for crypto, pgatour.com/masters.com for golf). These are where to look, not a certified cause. No NLP/news-correlation pipeline exists yet (see Suggestions P2-3).

F-11 · Est. notional is a derived, non-official metric

What: “Highest dollar amount” is operationalized as volume × last price. Kalshi does not publish “event dollar volume” as a field; this proxy overweights high-price contracts vs low ones and ignores fees/slippage. Alternatives (24h notional, open-interest × price) are one-line changes in kalshi.js#estNotionalOf.

F-12 · Fee maker/taker nuance in strategy P&L

What: the Strategy Lab deducts a taker fee on entry and exit, and none at resolution. Real Kalshi fee behavior for resting orders (maker) can be materially lower, and several series carry non-standard fees. Simulated P&L therefore skews pessimistic for limit-order strategies. Documented in strategies.js and on the Strategy Lab page.

F-13 · Demo account panel field mapping is defensive, not guaranteed

What: balance/positions/fills/orders renderers try fixed-point dollar fields first (*_fp, *_dollars) then legacy integer cents, and mirror the raw JSON below the tables for debugging. If your account tier returns different shapes, tables may show zeros or “—” — the raw pane is ground truth.

F-14 · GitHub Pages will serve this repository publicly

What: the repo is public and Pages is on. That means the dashboard is a public single-page app. Never paste production keys into it; demo keys stay in your own browser's localStorage. The site ships no secrets (verified: repo contains only these files; no keys, no .env).
