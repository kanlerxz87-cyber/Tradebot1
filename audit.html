This page records what was reviewed, what was re-run, what was fixed, and what could not be checked. It covers every implementation merged into this repository from the same brief. Where a value could not be confirmed it is marked unverified and left blank — never filled in by inference.

Read this first — the reviewing sandbox could not reach Kalshi. On 2026-11-22 this session's environment resolved only github.com, api.github.com and the package registries. Every Kalshi host returned HTTP 000 (no connection): https://external-api.demo.kalshi.co/trade-api/v2/exchange/status, https://demo-api.kalshi.co/trade-api/v2/exchange/status, https://docs.kalshi.com/getting_started/api_environments, and also the published site https://kanlerxz87-cyber.github.io/Tradebot1/. So this session could not re-fetch Kalshi documentation or market data. Every Kalshi fact below is therefore either (a) reproduced from the data file committed by the scheduled collector, which ran inside GitHub Actions where Kalshi is reachable, or (b) attributed to the session that recorded it, with the official link for your own check. Nothing is asserted as freshly re-verified when it was not.

2. Defects found and fixedEach was reproduced from committed evidence before being changed, and each now has a regression test that fails against the previous code.

#DefectEvidence it was realEffect a visitor sawFix
D1 Price history never accumulated: the collector read the whole history.json envelope instead of its series map, so each cycle started from an empty history. Two consecutive published cycles (commits 521e795, 73ef9dd) both stored exactly 2 points per market — it could never grow. The chart could not show more than one cycle of samples, and the “hours” range could never fill, although the brief asks for seconds / minutes / hours ranges. Read history_state["series"]. Test: test_history_accumulates_across_cycles.
D2 Settled markets were written with topic = null, and the page generator filters resolutions by topic. All 308 rows in the committed resolved.json had topic: null. Every topic page said “No settled markets recorded yet — resolution tracking starts with the first collection cycle” while 308 settled markets were in the data. Assign the topic from the official series taxonomy; backfill stored rows; generator falls back to the series taxonomy. Tests: test_resolution_rows_have_topic_and_own_market_url.
D3 The bounded settled sweep took the alphabetically first ten series across all topics. Tickers sort alphabetically, so KXAAAGAS* and elections consumed the ten slots; the committed 308 rows were 300 gas + 8 elections, and golf, culture and crypto had none. Those three topics could never show a resolution, whatever happened on the exchange. Sweep 6 series per topic. Test: test_sweep_reaches_every_topic_not_only_the_alphabetically_first.
D4 The published resolution table was capped at 120 rows globally. All 120 published rows were gas; elections' 8 rows were dropped from latest.json even after D2 was fixed. Elections would have shown an empty table on its own topic page. Cap per topic (60) plus an unattributed bucket. Test: test_published_resolutions_are_capped_per_topic.
D5 Resolution rows linked every row to one generic settlement-document page instead of the market itself. api_url was null on all 308 rows; both tables render api_url || source, so all rows fell back to the same generic URL. The brief requires a source link on every table row; a shared generic link does not let a reader verify that row. Rows now carry <rest_base>/markets/<ticker>. After the backfill all 308 rows have their own official URL.

After the fixes the committed snapshot renders 60 gas and 8 elections resolution rows, each with its own verify link. Golf, culture and crypto resolutions remain empty until the next scheduled collector cycle, because the sweep that would fetch them had never run under the old logic; the unit test proves the new sweep requests them. That is a timing fact, not a claim that rows exist.
