AUD-04 low

Simulated fees are rounded to the whole cent; the exchange rounds a fill to $0.000001 and aligns the balance to $0.0001

Both fee implementations round the formula's result up to the whole cent, which is what reproduces the printed summary table. It is not the per-fill rule: Fee Rounding states that a trade fee is rounded up to $0.000001 and the balance is then aligned to $0.0001 for a direct member, with a rebate accumulator across an order's fills. At 100 contracts and $0.05 the two rules differ by $0.0075 (0.34 versus 0.3325).

Impact. Every simulated P&L figure is at most one cent per fill pessimistic. The difference is disclosed here and next to the performance numbers rather than silently changed, because changing it would also rewrite historical results on the board.

Deciding source: VF-17 · VF-19 · VF-20

How to check: Compare the table's 100-contract column with Fee Rounding's worked examples. A direct member's net fee on 100 contracts at $0.05 is $0.3325 before balance alignment, not $0.34.

AUD-06 medium

The browser monitor still files elections on a deprecated field

docs/assets/core.mjs decides the 'elections' topic with event.category. Get Events marks category deprecated and points to the series-level category, and the EventData schema does not list category as required. If the field is absent this rule never matches and elections events are silently dropped from that monitor, with no error to notice.

Impact. One of the five briefed topics can go empty on docs/ without any visible failure. The desk and the board discover elections through series metadata and are unaffected.

Deciding source: VF-21

How to check: Compare the topic rule in docs/assets/core.mjs with the EventData schema in Get Events. The fix is to join the series ticker to GET /series, which is a change to a file this session does not own.

AUD-07 low

A topic comment disagrees with the same session's own captured probe

tools/topics.mjs says the Culture discovery request returns 'exactly 1 series (KXXBANNEDGROK)'. The probe recorded in data/snapshot.json for the same request against the same demo root returns two: KXXBANNEDGROK and KXXBANNEDMURRAYHILLGUY1. A reader tracing the rule by hand would think the rule was broken.

Impact. Documentation only: the code and the capture agree with each other, the comment does not.

Deciding source: VF-01

How to check: Read the Culture probe in data/snapshot.json -> discoveryProbes and compare with the header comment in tools/topics.mjs.

AUD-10 low

Two sessions disagree about Culture, and both are right about different roots

One implementation reports that no Culture category exists and maps the topic to Entertainment; another captured GET /series?category=Culture against the demo root and got two series. The demo and production catalogues differ, so neither statement refutes the other, but a reader of the site sees only one of them at a time.

Impact. A trader could believe culture coverage is missing when the demo catalogue has it, or vice versa. No number on any page is wrong.

Deciding source: VF-01

How to check: Read discoveryProbes in data/snapshot.json (root recorded per probe) next to docs/desk/topics/culture.html (production catalogue).

AUD-11 low

The desk still labels a now-verifiable fee model UNVERIFIED

kalshi_trader/fees.py sets VERIFIED = False and explains that the fee schedule could not be retrieved. The schedule is retrievable and is the source now quoted here: the taker rate, the maker rate and the maker default all match the code. The label is honest about the session that wrote it but is now wrong about the model, and every ledger row carries the stale label.

Impact. Readers discount performance figures that are, for the formula, correctly modelled. The remaining real caveat is the rounding in AUD-04.

Deciding source: VF-17 · VF-18

How to check: Compare TAKER_RATE and MAKER_RATE in kalshi_trader/fees.py with the two formulas in the fee schedule PDF.

AUD-12 low

`or` fallbacks hide a genuine zero quote behind the legacy field

Values are read as first_float(...) or price_from_cents(...). A leg whose real fixed-point value is 0.0 is falsy, so the reader falls through to the legacy cent field, which may be absent (None) or stale. The result is None or an old price where the true value is zero.

Impact. Low: zero prices are the boundary of the book, and downstream guards treat them as an empty side anyway. It is still the wrong way to choose between two representations.

Deciding source: VF-09 · VF-13

How to check: normalize_market({'yes_bid_dollars': '0.0000', 'yes_bid': 42}) returns 0.42, not 0.0. Use an explicit None check instead of `or`.

AUD-13 info

The documented 'recommended' production host is not the one most code uses

The desk and the Node client default to api.elections.kalshi.com for production reads. That host is documented as supported, so no request is wrong, but external-api.kalshi.com is the recommended host for API traders. Nothing in this repository needs to change for correctness; a future session may want to switch the default.

Impact. None today: both hosts are supported and serve the same data.

Deciding source: VF-03

How to check: Read the environment table in API Environments and Endpoints, column 'Also supported'.
